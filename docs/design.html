Dragon Ball Z: Kakarot on Steam · standard and HD builds

Kakarot HD Save Syncer: design

The plugin that keeps the two builds' saves in step across devices. How the game saves, loads and transfers, and what Steam's index is, are covered by the Game Save & Save Transfer Mechanism page and are assumed here.

Proposed · 2026-10-25

1. Goal and requirements

Play either build on any device and pick up where you left off in the other build on any other device, with the in-game save list correct, with no manual step and without the HD menu's Transfer Save Data. The primary case is HD on a Windows desktop and the standard build on a Steam Deck, with Steam Cloud between them.

Must hold

  • After every save in one build, the same slot exists in the other build's format and in Steam's index.
  • The other build's save list shows the slot with its thumbnail, play time and progress.
  • Both directions.
  • One install on one machine is enough for the primary case; installing in both builds or on several machines also works.
  • No conflict handling of its own beyond what Steam already does.
  • Never deletes a save on its own.
  • Survives alternating builds on one device, a slot deleted on either side, a build that has never run, cloud off or offline, and a crash mid-save.

Out of scope

  • Non-Steam storefronts, which have no Remote Storage index.
  • The card-game save, which the transfer never touches.

Terms

own / foreign
From the plugin's point of view: own is the build it is loaded in, foreign is the other build. Own files are the ones that build reads and writes natively.
output
A file the plugin produced from a file of the other build.
reconcile pass
The per-slot check the plugin runs once at startup, section 5.
manifest
The plugin's record of which outputs it produced from which sources, kept in the game's cloud folder, section 6.

2. Topology for the primary case

Both builds share one Steam app ID and one cloud folder, and the plugin can run in either build. So the desktop plugin alone covers both directions: it produces standard-format files when HD saves, and it folds the Deck's native standard saves into HD at the next HD launch. A Deck-side install is possible under Proton with a launch-option DLL override, but it is not needed and not the recommended path.

3. The two operations

Everything the plugin writes comes from one of two operations. Standard to HD reproduces the native transfer byte for byte; HD to standard is its exact inverse, verified to round-trip. The Python tools in the repo perform both.

Convert a game save

ManualSaveX ↔ ManualSaveRX, AutoSave0 ↔ AutoSaveR0. Decrypt, replace the engine header with the target build's, restamp the version with the target build's current value, re-pad, re-encrypt. The game state is untouched.

Merge a Headers[slot] entry

Copy the slot's Headers[slot] entry from the source build's system save into the target build's, leaving the target's consent flags, settings and everything else alone. Only if the target build has no system save at all is the source one converted whole: engine header, version stamp, and the per-build fields (the three standard-only flags and IsConversion) dropped or set as the native transfer does.

Wherever a target engine header and version stamp are needed, they come from a reference: the newest file the target build wrote. This follows game patches with nothing hardcoded. With no reference on this machine, the game save keeps its source header and stamp, which both builds load, until the other build has run once. The AES key is located at runtime and never stored. All reads and writes go through Steam's Remote Storage API from inside the game process, never directly to the folder.

4. At save time: the write hook

The same sequence runs in reverse when the plugin is loaded in the standard build. The plugin hooks the FileWrite entry of the Remote Storage interface. When the game writes one of its own slots, the hook lets the write complete and then, before returning, converts that slot, merges its entry into the foreign system save, writes both through the same API and records them in the manifest. Because it runs synchronously on the game's thread, it is finished before the game can do anything else, including exit.

Nothing needs to hold the game open for the upload; the Steam client uploads pending index entries itself, at exit and often during play, whatever wrote them.

5. At startup: the reconcile pass

The pass runs once per launch over every slot, the autosave included. It is triggered by the game's first read of its own system save, so that it completes before the game lists anything, and after Steam has synced and initialised.

Comparison uses the save timestamp inside the Headers[slot] entry, not the file time. File times differ across devices and clocks and Steam rewrites them on sync; the entry's timestamp is written by the game and is identical in a file and its converted copy. That identity is what makes "same timestamp, nothing to do" safe: a copy the plugin produced itself compares equal and is never re-converted. "Own newer" covers an output lost to a crash or overwritten by the game mid-session.

When only one side exists, the manifest decides. If it links the surviving file to the missing one, the missing one was deleted on purpose on some device and the survivor is left alone; the plugin never deletes anything itself, and a stale slot showing on one side is the accepted price. If there is no link, it is a save the other build has never seen and it is converted or produced. During play, a FileDelete hook records the deletion in the manifest for the same reason.

6. The manifest

A small file recording, for each output, the slot, the direction, and the hashes of the source file and the output. It exists to answer one question the files cannot: when a slot exists on only one side, was the other side deleted deliberately, or has it never been produced? Everything else the pass needs comes from the timestamps.

It is written through the same Remote Storage API as the saves, into the game's cloud folder, so it travels with them and is in sync with them by construction: whichever device the files reach, the links that describe them reach too. Kept locally only, it would be missing on a second plugin-equipped machine or after a reinstall, and a slot deleted on one side would be produced again from the other. The game's save list comes from the system save, not from the folder's contents, so the extra file is invisible to it. A local copy is kept for cloud-off use.

Losing the manifest is harmless for data: the worst case is a slot deleted on one side being produced again on the other.

7. Steam Cloud and conflicts

Steam downloads cloud changes only at launch, never into a running game, so foreign files cannot change under a session. The save-time hook therefore never has to check anything: the session started from the newest data and the player has moved on from it.

If two devices saved the same slot without a sync in between, Steam detects the clash on the files themselves and shows its keep-local-or-cloud prompt before the game starts. The reconcile pass runs on whatever that choice left on disk. The plugin has no conflict logic of its own.

8. Cases

CaseWhat happens
HD on desktop, standard on Deck, plugin in HD onlyHD saves are produced in standard format at save time; the Deck saves natively; the next HD launch converts them in. Deck untouched.
Both builds on one device, plugin in oneSame as above without the cloud. Works offline.
Plugin in both builds, or on several machinesEach build runs the pass and the hook; equal timestamps keep them from re-converting each other's outputs, and the shared manifest keeps deletions from resurrecting.
Slot deleted on either sideNever propagated automatically. The manifest stops the survivor from being produced again; the deleted side stays empty until the user saves there.
Both games running at onceSteam blocks this for one app ID. If forced, a game may overwrite a merged entry from memory; the next pass sees "own newer" and merges it again.
Other build has never runGame saves keep the source header and stamp; the system save is converted whole. The other build's first run becomes the reference.
Crash during a saveThe output may be missing; the next pass sees "own newer" and produces it.
Mixed patch levels across devicesA build that rejects the other's version stamp rejects that build's own saves just the same. Not ours.
Cloud disabled or offlineFully local; uploads queue until online.

9. Distribution and implementation

Install

One zip: Ultimate ASI Loader as xinput1_3.dll plus kakarot-hd-save-syncer.asi, dropped into the exe folder of whichever build the user plays on Windows. That is the whole install for the primary case. Installing into both build folders is supported.

Components

  • AES-256 ECB and the runtime key lookup
  • Save-file parsing sufficient for the two operations
  • Remote Storage access through the game's own Steam session, with hooks on write, read and delete
  • Build detection and reference-file discovery
  • The manifest, stored through the same API in the game's cloud folder

C++ ASI with no dependencies beyond the Windows SDK. The Python tools are the oracle: for every operation the C++ output must be byte-identical to the Python output, which is itself byte-identical to the native transfer for standard to HD and round-trips exactly for HD to standard.

10. Open items

  1. Confirm the Remote Storage interface layout in each build's bundled Steamworks before hooking; the two builds ship different Steamworks versions.
  2. Confirm the game's first system-save read happens on a thread where a few hundred milliseconds of reconcile work is acceptable. If not, run the pass on plugin load after Steam initialises and block that first read until done.
  3. Whether to offer deletion propagation as an opt-in setting. The default stays off.
