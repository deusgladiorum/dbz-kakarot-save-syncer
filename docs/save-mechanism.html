Dragon Ball Z: Kakarot on Steam · standard and HD builds

DBZ: Kakarot Game Save & Save Transfer Mechanism

How each build of the game, meaning the standard version and the HD remaster, which are two separate executables, serializes, encrypts, stores and loads its save files, and what the HD build's Transfer Save Data does to them. Found by reverse engineering.

1. The save/load path, per build

Each build runs this path on its own, against its own files (ManualSave0 for standard, ManualSaveR0 for HD) and its own entries in Steam's index, the per-game list of files Steam knows about. Neither build touches the other's files unless you use Transfer Save Data, the HD build's menu option that imports standard saves.

On save, the game state is serialized into an Unreal GVAS object and encrypted using AES-256 ECB via a key embedded in the build's executable. Both standard and HD builds use the same key. The encrypted file is not written to the disk directly. Instead, the game calls Steam's Remote Storage API, which separately writes to both Steam's per-game file index (remotecache.vdf) and the game's save directory. On load, the same process happens in reverse, with the existence check for the chosen slot consulting Steam's index rather than the folder. A file manually copied into the folder without also storing it in the index would fail to load.

2. Save file layout and transfer explanation

The HD build's Transfer Save Data rewrites only the orange parts and carries everything else over unchanged. For a game save that is the engine header and the version stamp. For the system save it also drops the three flags the HD class does not have and sets IsConversion, and "carrying over" means merging into the existing HD system save, which is how the slot's Headers entry arrives there.

3. Which file holds what

Only the R suffix separates the two builds' file names, and both builds keep their files in the same folder. Because the list reads Headers from the system save, copying a game save alone leaves the list showing the old thumbnail and play time, or no entry at all for a slot the system save has never seen.

4. Native transfer versus a plain file copy

The index decides whether a slot loads. A copied file for a slot the HD build never saved is not found. A copied file whose slot name was already indexed loads, but the list keeps that slot's old Headers entry. The system save is untouched either way.

Facts worth remembering

Save folder
<Steam>\userdata\<user>\851850\remote with the index in remotecache.vdf one level up.
Version stamps
Standard: 544 then 560. HD: 304 then 320. Each build restamps its own value on every save; the number moves with game patches.
Version acceptance (HD)
Loads if the stamp is ≥ 400 or ≤ 320, rejects 321 to 399 as a version error. Nothing else reads it. The standard build's rule has not been traced.
Encryption
Unreal's stock FAES: AES-256-ECB, key = first 32 characters of a 128-character string embedded in each exe. Same key in both builds.
Load errors
The game distinguishes: not found (index miss), corrupt, out of storage, version, DLC data not owned.
Engine versions
Standard build is Unreal 4.21.2, HD build is 4.27.2. Each loads the other's header without complaint.
